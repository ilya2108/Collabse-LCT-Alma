# Отчёт нагрузочного тестирования — 300+ одновременных пользователей

Отчёт по решению кейсодержателя (Q&A 16.09, OVERVIEW.md §8.1, N3): собственный отчёт
нагрузочного тестирования и план масштабирования на 300+ одновременных пользователей.
Требования ТЗ к нагрузке (50 пользователей, 10 параллельных отчётов) — §8.
Методика и расчёт ёмкости — `../design/deployment.md` §8; сценарий и запуск —
`deploy/load/` (k6). Отчёт составлен по фактическому прогону, а не по смоук-тесту.

## 1. Стенд и методика

| Параметр | Значение |
|---|---|
| Дата прогона | 16.09.2026, 17:10–17:20 UTC |
| Стенд | k3d (1 server + 1 agent) на одной машине; Docker VM: 10 CPU, 8 GiB |
| Развёртывание | `make k8s-up && make demo` — штатный демо-стенд, без спец-настроек |
| Backend | 2 реплики на старте; HPA `cpu: 70%`, min 2 / max 6; requests 200m/256Mi, limits 1 CPU/512Mi |
| Генератор | k6 0.57 в Docker на той же машине (`deploy/load/k6-script.js`) |
| Аутентификация | confidential-клиент `crm-loadtest` (Direct Access Grants только у него), пользователь `kam1@demo` (роль kam) |
| Модель VU | КАМ с think-time 5–15 с: канбан → реестр (заявки/вузы/студенты) → карточка; каждый 10-й VU — валидный переход по процессу (version из карточки, 409 — легитимный отказ optimistic locking) |

Профиль (полный, без SMOKE): разгон 2 мин 0→300 VU → полка 5 мин 300 VU →
пик 1 мин 300→400 VU («300+») → спад 1 мин 400→0.

**Thresholds (SLA, зашиты в скрипт):** `http_req_failed rate<0.01` ·
`http_req_duration p(95)<500 p(99)<1000` (мс) · `checks rate>0.99`.

## 5. Разбор отклонений — честно

1. **p99-хвост на разгоне (17:11–17:12, без ошибок).** Пока HPA не отмасштабировал
   backend с 2 до 6 реплик (~60 с: порог 70% CPU + прогрев новых подов), 2 реплики
   держали ~230–300 VU — p99 кратковременно до 3 с. Это стоимость холодного старта
   масштабирования, не стационарный режим: уже с 17:13 p99 = 117 мс.
2. **Всплеск 89 × HTTP 500 в одном 10-секундном окне (17:16:40–17:16:50).**
   По логам backend: `asyncpg.exceptions.TooManyConnectionsError: sorry, too many
   clients already`. Пул SQLAlchemy живёт в каждом процессе uvicorn, а процессов на
   под два (`--workers 2`). Поэтому верхняя граница была
   6 реплик × 2 воркера × (pool 10 + overflow 10) = **240 соединений** при
   `max_connections=100` у PostgreSQL. К этому добавлялся пул Keycloak, у которого по
   умолчанию до 100 соединений. В первой редакции отчёта здесь стояло 120: воркеры не были
   учтены. При мгновенном всплеске конкурентности пулы раскрылись в overflow и упёрлись в
   лимит СУБД. В бюджет ошибок SLA это укладывается (0.28% < 1%), но для плана
   масштабирования это главный вывод прогона — см. §6.

   **Исправлено после прогона** (проверяется тестом `backend/tests/test_connection_budget.py`
   по тем же манифестам, что применяет `kubectl apply -k`):

   | Потребитель | Расчёт | Соединений |
   |---|---|---|
   | backend | (maxReplicas 6 + maxSurge 2 при rolling update) × 2 воркера (`WEB_CONCURRENCY`) × (`DB_POOL_SIZE` 4 + `DB_MAX_OVERFLOW` 2) | 96 |
   | Keycloak | `KC_DB_POOL_MAX_SIZE` | 10 |
   | Jobs | seed-demo 6 + db-migrate 1 + demo-reset 2 | 9 |
   | резерв суперпользователя | `superuser_reserved_connections` | 3 |
   | **итого** | | **118 < `max_connections=150`** |

   На VPS (HPA max 4) получается (4 + 1) × 2 × 6 + 22 = 82. Повторный прогон с новыми
   значениями ещё не выполнялся. Его методика — §8, результаты будут добавлены по факту.

## 6. Выводы и план масштабирования на 300+

- **300 одновременных пользователей стенд держит**: на стационарной полке
  p95 = 36–80 мс, p99 = 84–230 мс, ошибок 0; пик 400 VU — p95 = 41 мс.
  SLA-пороги p95 и error-rate выполнены с многократным запасом; p99 формально
  превышен на 7% транзиентами разгона (см. §5.1) — стационарный p99 внутри порога.
- HPA отрабатывает в обе стороны на глазах: 2 → 6 реплик за ~60 с под нагрузкой
  и обратно до 2 после снятия (лог в §4) — план «реплики + балансировка» живой.
- **Действия по итогам прогона**:
  1. бюджет соединений согласован с ёмкостью СУБД (сделано, §5.2): `DB_POOL_SIZE=4`,
     `DB_MAX_OVERFLOW=2` на процесс, пул Keycloak ≤ 10, `max_connections=150` у
     PostgreSQL. Старое предложение `DB_MAX_OVERFLOW=6` давало 6 × 2 × 16 = 192 > 100,
     то есть не решало проблему. В целевой архитектуре перед PG стоит pgbouncer;
  2. для мгновенного старта под нагрузкой можно поднять minReplicas на время
     пиковых кампаний (HPA-параметры — в overlay, без пересборки).
- Расчёт ёмкости и целевая топология: `../design/deployment.md` §8.4.

## 7. Воспроизведение

```sh
make k8s-up && make demo            # стенд + сид (≥ 50 заявок)
make load-test                      # локальный k6; артефакты сохраняются локально
# либо docker-вариант без бинаря k6 — deploy/load/README.md
kubectl -n crm get hpa backend -w   # реплики 2→6→2 параллельно с прогоном
```

Сырые артефакты прогона `load-raw.json` (посекундные метрики, ~43 МБ) и
`load-summary.json` сохраняются локально при прогоне и в git не попадают (`.gitignore`);
таблицы §3–§4 посчитаны из них (перцентили — по минутным корзинам).

## 8. НФТ ТЗ: 50 пользователей и 10 параллельных отчётов — методика

Прогон 16.09 этих требований не проверял. Все VU работали под одной учёткой `kam1@demo`,
а отчёты и выгрузки в сценарии не вызывались. Для НФТ в `deploy/load/k6-script.js`
добавлены профили:

| Профиль | Нагрузка | Пороги в скрипте |
|---|---|---|
| `users50` (`make load-test-users`) | 50 VU под 5 учётками разных ролей, путь КАМа, 5 минут | ошибки < 1 %, экраны p95 < 500 мс и p99 < 1 с |
| `reports` (`make load-test-reports`) | 10 VU строят разные отчёты (10 кодов) со случайными периодом и фильтрами, холодный кэш, каждая третья итерация — выгрузка XLSX/PDF со скачиванием | отчёт p95 < 1 с, выгрузка p95 < 3 с (цель команды) |
| `nft` (`make load-test-nft`) | оба профиля одновременно | все пороги выше |

Подробная методика (учётки, фильтры, почему кэш холодный, что снимать параллельно) —
`deploy/load/README.md`, раздел «Методика НФТ». Перед прогоном и после него стенд
сбрасывается к эталону (`make demo-reset`).

**Статус: прогон не выполнялся, результатов нет.** Таблицы по образцу §2–§4 (p50, p95, p99
по каждому отчёту и выгрузке, ошибки, реплики HPA, пик соединений PostgreSQL) будут
