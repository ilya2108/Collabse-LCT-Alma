# Соответствие техническому заданию

Построчная трассировка требований технического задания к местам реализации.
Развёрнутая версия с деталями — [`../design/OVERVIEW.md`](../design/OVERVIEW.md) §8.

## Процессы (движок workflow — ядро системы)

| Требование | Где реализовано |
|---|---|
| Два процесса: B2B (вузы) и B2C (физлица + юрлица) | 2 графа в БД (`workflow` b2b/b2c), переключатель доски заявок; демо-данные обоих графов с ветвлениями и возвратами |
| В B2C — возможность добавлять новые варианты взаимодействия | редактируемый справочник `interaction_type` + конструктор процессов добавляет этапы/переходы без кода |
| Процесс един для всех внутри типа, версионирование запрещено | одна живая схема, мутация in-place, version-полей нет ([`../design/workflow-engine.md`](../design/workflow-engine.md) §2.1) |
| Изменения применяются сразу для всех | согласование = атомарное применение одной транзакцией; SSE-событие `workflow.changed` перестраивает все открытые доски |
| Ветвления | несколько исходящих переходов + `condition`-подсказка; доска заявок подсвечивает разрешённые колонки |
| Возвраты на предыдущие шаги | переходы `kind: return` с обязательным комментарием (CHECK в БД); красный пунктир в конструкторе |
| При изменении «на лету» заявки сопоставляются, работа не встаёт | миграция заявок в транзакции применения; advisory-локи PostgreSQL: переходы не блокируются вне окна применения; история `migrated` |
| Переименование/удаление статуса — только с согласованием администратора | опасные операции всегда `pending` + посимвольный ввод имени (`confirm_name`) + подтверждение только admin (`/admin/approvals`) |
| При удалении статуса заявки переносятся на соседний (лучше предыдущий) | `migrate_to_status_id` обязателен, только сосед по ребру, по умолчанию — предыдущий этап |
| Один вуз: договор один, продуктов несколько | `contract` + `contract_product` M:N; второй активный договор — предупреждение, не запрет |
| Параллельных взаимодействий ≤ 2, без переусложнения | несколько открытых заявок на вуз без constraint, предупреждение при третьей; КАМ читает всё / пишет своё |

## Авторизация и роли

| Требование | Где реализовано |
|---|---|
| Keycloak в собственной инфраструктуре | self-hosted Keycloak 26, `start --import-realm` из ConfigMap, БД в том же PostgreSQL |
| RBAC по ролям; отображение интерфейса строго по ролевой модели | роли `admin`/`head_kam`/`kam`/`observer`; `permissions` из `GET /auth/me`; фронтенд скрывает разделы, backend дублирует каждую проверку |
| Публичное описание демо-пользователей по ролям | таблица демо-пользователей в README; все данные для входа публичны |

## Интеграции

| Требование | Где реализовано |
|---|---|
| CRM↔LMS и CRM↔CMS двусторонние, на заглушках; двусторонность проверяема | 4 направления на одном JSON-конверте; заглушки — отдельные поды с журналом обмена в интерфейсе (`lms.crm.localhost`, `cms.crm.localhost`); монитор `/admin/integrations` с журналом ←/→ |
| JSON по API; допустим асинхронный обмен через шину | конверт `IntegrationEvent`; режим `http` (HMAC-подпись, ретраи, DLQ) реализован; `stream` (KeyDB Streams) — в плане развития: настройка `integration_mode` принимается, транспорт пока не переключает |
| Состав JSON: статус, ответственный, вуз, программа, продукт + ключи БД и S3 | payload ровно из пяти блоков + `links.db_keys` / `links.s3_keys` ([`../design/api-contract.md`](../design/api-contract.md) §13.1) |
| Догрузка обезличенных данных без изменения схемы | схема не меняется: пополняются словарь синонимов сопоставления колонок и демо-данные |
| Обогащение из открытых источников — только разовая предзагрузка, без выхода в интернет во время работы; диалоговое окно в админке | `/admin/dictionaries` + тот же мастер импорта (JSON/таблицы); у ядра нет egress по NetworkPolicy — «двойной ответ» кодом и сетью |

## Импорт/экспорт и отчёты

| Требование | Где реализовано |
|---|---|
| XLSX **и XLS** (старый Excel); устойчивость к битым кодировкам | формат по магическим байтам (`openpyxl` / `xlrd 2.x`); charset-normalizer с перебором utf-8-sig → utf-8 → cp1251 → koi8-r → cp866; экспорт CSV utf-8(BOM)/cp1251 |
| Сопоставление полей — интерактивный диалоговый менеджер | 5-шаговый мастер импорта: автопредложение сопоставления + ручной выбор + шаблоны + построчный отчёт ошибок |
| Отчёты: интерактивные аналитические панели с экспортом в растровые/файловые форматы | собственная реализация на ECharts: фильтры, детализация, PNG в один клик (`getDataURL`), XLSX/CSV через задания экспорта |

Аттестация импорта/экспорта на реальных «грязных» данных — [`import-export-test.md`](import-export-test.md).

## Данные и 152-ФЗ

| Требование | Где реализовано |
|---|---|
| PostgreSQL + MinIO S3 | PostgreSQL 16 (35 таблиц) + MinIO (3 бакета); StatefulSet + PVC |
| Студенты: ФИО + email, шифрование/обезличивание в БД | Fernet-шифртекст + HMAC blind index для поиска + псевдонимизация `display_name` «Фамилия И.О.»; маскирование всем, раскрытие только с аудитом |
| Безопасность библиотек; закрытый контур | зафиксированные версии, `uv.lock`/`package-lock.json`, `pip-audit`/`npm audit`; без CDN; default-deny NetworkPolicy |
| ЭЦП тестировать не нужно | в системе отсутствует осознанно |

## Архитектура и нефункциональные требования

| Требование | Где реализовано |
|---|---|
| Монолит с функциональными переключателями или микросервисы (+minikube/k3s) | модульный монолит + функциональные переключатели (`/admin/feature-flags`) + полноценный Kubernetes с **обоими** overlay: k3d(k3s) и minikube; доказательства живого кластера — [`k8s-evidence.md`](k8s-evidence.md) |
| Кэш KeyDB (легковеснее Redis): карточки, документы, страницы; без оффлайн-режима | cache-aside `crm:v1:*` (карточки, списки, панели), TTL-коды бота, pub/sub для SSE; деградация в PostgreSQL при недоступности; оффлайн-режима нет |
| Нагрузка: собственный отчёт; план масштабирования на 300+ | k6-сценарий 300→400 VU с порогами SLA (`deploy/load/`), HPA backend 2→6, расчёт ёмкости ([`../design/deployment.md`](../design/deployment.md) §8); отчёт прогона — [`load-report.md`](load-report.md) |
| Диаграммы: C4/BPMN, связей, программно-аппаратная, БД | C4 контекст+контейнеры, ERD ×4, sequence/state, топология и DMZ-контур — по всем документам `../design/` |
| Мобильная версия не нужна — адаптивная вёрстка | адаптив до планшета, перетаскивание карточек с сенсорного экрана; мобильного приложения нет |
| LLM — только если реально дополняет; не приоритет | не делаем; переключатель `llm_features` выключен с подписью «в закрытом контуре — выключено» |
| Ранжирование программ — ручное; автоформула — бонус | `priority_rank` (меньше = выше), перетаскивание/▲▼ с аудитом; расчётный режим — за функциональным переключателем |
| Встроенный обмен сообщениями: в идеале да, заглушки допустимы | комментарии заявки: @упоминания, вложения из MinIO, обновление в реальном времени по SSE |
| Удобство интерфейса важнее брендбука | токен-слой Tailwind v4 + shadcn/ui под дизайн-систему «Ростелекома» gen2 ([`../design/redesign.md`](../design/redesign.md), [`../design/brand-rt.md`](../design/brand-rt.md)), туры адаптации сотрудников, принцип «ноль тупиков» |

## Telegram-бот

| Требование | Где реализовано |
|---|---|
| Служба уведомлений с абстракцией каналов: Telegram (реальный), Max/Email — подключаемые | `services/notification`: адаптеры каналов; статусы active/stub в настройках |
| Авторизация бота через тот же Keycloak, привязка по одноразовому коду | код 6 цифр (TTL 10 мин, KeyDB GETDEL) → бот под client credentials `crm-notification` → `POST /internal/bot/bind` → `app_user.tg_chat_id` |
| Команды бота — строго по ролевой модели | `/my`, `/stuck`: backend резолвит chat_id → пользователь и применяет его RBAC; непривязанный получает отказ |
| «Зависшие»: настраиваемый порог 1–2 недели, эскалация ответственному и руководителю | порог в днях (по умолчанию 14, каскад правило→этап→процесс→настройка); 1×порога — ответственному, 1.5× — руководителю (`manager_id`); дедупликация уведомлений |
| Адресация: по нику Telegram, email или роли — настраиваемо | `notification_rule.recipient_type`: responsible / manager / role / user / tg_username / email |
| Закрытый контур: шлюз уведомлений в DMZ, отразить на диаграмме | NetworkPolicy: notification — единственный egress; диаграмма в README и [`../design/deployment.md`](../design/deployment.md) §3.11 |

## Пул талантов

| Требование | Где реализовано |
|---|---|
| Карточка студента: ФИО, email, вуз, программа, федпроект, воронка кандидат→…→пул талантов | `student` + 4 статуса воронки + история переходов |
| Привязка к расписанию активностей и B2C-процессу | `activity` + `activity_schedule` (единый календарь) + связь с B2C-заявкой через контрагента |
| Загрузка списков XLSX/XLS/JSON через тот же диалоговый импорт | общий конвейер импорта `entity_type=students`, дедупликация по blind-index email |
| Шифрование/псевдонимизация; файлы в MinIO | тот же контур защиты ПДн (Fernet + HMAC); резюме/сертификаты — `crm-files`; наблюдатель файлов не видит |
| Выгрузки, фильтры, уведомления | фильтры/пресеты/экспорт; событие `student.talent_pool_added` → служба уведомлений |

## Осознанно за рамками системы

Оффлайн-режим, мобильное приложение, ЭЦП, обогащение из интернета во время
работы, версионирование процессов — отсутствуют в схеме БД, API и интерфейсе
**намеренно**, в соответствии с техническим заданием.
