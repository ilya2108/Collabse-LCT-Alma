# Соответствие техническому заданию

Построчная трассировка требований технического задания к местам реализации.
Развёрнутая версия с деталями — [`../design/OVERVIEW.md`](../design/OVERVIEW.md) §8.
Доработки после первой версии собраны в конце документа.

## Процессы (движок workflow — ядро системы)

| Требование | Где реализовано |
|---|---|
| Два процесса: B2B (вузы) и B2C (физлица + юрлица) | 2 графа в БД (`workflow` b2b/b2c), переключатель доски заявок; демо-данные обоих графов с ветвлениями и возвратами; роли можно ограничить одним процессом |
| В B2C — возможность добавлять новые варианты взаимодействия | редактируемый справочник `interaction_type` + конструктор процессов добавляет этапы/переходы без кода |
| Процесс един для всех внутри типа, версионирование запрещено | одна живая схема, мутация in-place, version-полей нет ([`../design/workflow-engine.md`](../design/workflow-engine.md) §2.1) |
| Изменения применяются сразу для всех | согласование = атомарное применение одной транзакцией: схема, перенос заявок, история, уведомления и аудит — либо всё, либо ничего; SSE-событие `workflow.changed` перестраивает все открытые доски |
| Ветвления | несколько исходящих переходов + `condition`-подсказка; доска заявок подсвечивает разрешённые колонки |
| Возвраты на предыдущие шаги | переходы `kind: return` с обязательным комментарием (CHECK в БД); красный пунктир в конструкторе |
| При изменении «на лету» заявки сопоставляются, работа не встаёт | перенос заявок удаляемого этапа — один SQL-оператор (CTE `UPDATE … RETURNING` → история) в транзакции применения; advisory-локи PostgreSQL: переходы берут shared, применение — exclusive, затем строки заявок (`FOR UPDATE`) — единый порядок, без deadlock; ожидание ограничено `lock_timeout` (переход — 10 с, применение — 30 с) → `409 workflow_busy` с `Retry-After`, клиент сам повторяет до 10 с; чтение не блокируется никогда. Замер: 10 000 заявок — лок 0,59 с против 25,1 с поштучно, 50 000 — 2,9 с против 130 с ([`migration-benchmark.md`](migration-benchmark.md), workflow-engine.md §6.3–6.8); история `migrated` |
| Переименование/удаление статуса — только с согласованием администратора | опасные операции всегда `pending` + посимвольный ввод имени (`confirm_name`, повторная сверка под локом) + подтверждение только с правом `workflow:approve` в процессе (из системных ролей — admin; `/admin/approvals`) |
| При удалении статуса заявки переносятся на соседний (лучше предыдущий) | `migrate_to_status_id` обязателен, только сосед по ребру, по умолчанию — предыдущий этап; срок нахождения на этапе сохраняется — зависание не маскируется; ответственные получают по одному сводному уведомлению вместо сообщения на каждую заявку |
| Один вуз: договор один, продуктов несколько | `contract` + `contract_product` M:N; второй активный договор — предупреждение, не запрет |
| Параллельных взаимодействий ≤ 2, без переусложнения | несколько открытых заявок на вуз без constraint, предупреждение при третьей; КАМ читает всё / пишет своё |

## Авторизация и роли

| Требование | Где реализовано |
|---|---|
| Keycloak в собственной инфраструктуре | self-hosted Keycloak 26, `start --import-realm` из ConfigMap, БД в том же PostgreSQL; Keycloak отвечает за вход, роли из realm — только стартовое назначение при первом входе |
| RBAC по ролям; отображение интерфейса строго по ролевой модели | роли и права хранятся в БД Альмы (`app_role`, `app_role_permission`, `app_user.roles`): каталог из 60 прав определяет код, 4 системные роли (`admin`/`head_kam`/`kam`/`observer`) + свои роли, которые администратор создаёт в интерфейсе «Роли и права» без программиста; область роли — процессы B2B/B2C и «все заявки / только свои»; права из `GET /auth/me`, фронтенд скрывает разделы и действия, backend дублирует каждую проверку (объект вне области — 404); изменения применяются без перезахода (SSE `access.changed`); защита от потери управления (admin заблокирован, последнего администратора не снять, аварийный `app.tools.rbac grant-admin`); всё в журнале аудита ([`../design/ux.md`](../design/ux.md) §3, §14.8) |
| Публичное описание демо-пользователей по ролям | таблица демо-пользователей в README; все данные для входа публичны; демо-роли «КАМ B2B» / «КАМ B2C» засеяны |

## Интеграции

| Требование | Где реализовано |
|---|---|
| CRM↔LMS и CRM↔CMS двусторонние, на заглушках; двусторонность проверяема | 4 направления на одном JSON-конверте; заглушки — отдельные поды с журналом обмена в интерфейсе (`lms.crm.localhost`, `cms.crm.localhost`; на публичном стенде — `lms`/`cms.crm.168-113-158-10.nip.io`); монитор `/admin/integrations` с журналом ←/→ |
| JSON по API; допустим асинхронный обмен через шину | конверт `IntegrationEvent`; источник истины — outbox в PostgreSQL (событие пишется в одной транзакции с операцией), доставка асинхронная по HTTP с HMAC-подписью, ретраями и DLQ; настройка `integration_mode` принимает только `http` (иное — `400 validation_error`); корпоративная шина (Kafka/ESB) подключается новой реализацией транспорта без смены конверта, outbox, ретраев и DLQ |
| Состав JSON: статус, ответственный, вуз, программа, продукт + ключи БД и S3 | payload ровно из пяти блоков + `links.db_keys` / `links.s3_keys` ([`../design/api-contract.md`](../design/api-contract.md) §13.1) |
| Догрузка обезличенных данных без изменения схемы | схема не меняется: пополняются словарь синонимов сопоставления колонок и демо-данные |
| Обогащение из открытых источников — только разовая предзагрузка, без выхода в интернет во время работы; диалоговое окно в админке | `/admin/dictionaries` + тот же мастер импорта (JSON/таблицы); у ядра нет egress по NetworkPolicy — «двойной ответ» кодом и сетью |

## Импорт/экспорт и отчёты

| Требование | Где реализовано |
|---|---|
| XLSX **и XLS** (старый Excel); устойчивость к битым кодировкам | формат по магическим байтам (`openpyxl` / `xlrd 2.x`); charset-normalizer с перебором utf-8-sig → utf-8 → cp1251 → koi8-r → cp866; экспорт CSV utf-8(BOM)/cp1251 |

| Отчёты: интерактивные аналитические панели с экспортом в растровые/файловые форматы | собственная реализация на ECharts: фильтры, детализация, PNG в один клик (`getDataURL`), XLSX/CSV/PDF через задания экспорта (PDF — серверный, fpdf2 со шрифтами DejaVu внутри пакета); отчёт «Активность КАМов» — какой КАМ за период с какими вузами работал и на каких этапах остановились заявки, с детализацией для руководителя и сводкой для заказчика, выгрузка PDF и многолистовой XLSX ([`../design/ux.md`](../design/ux.md) §6.4) |

## Архитектура и нефункциональные требования

| Требование | Где реализовано |
|---|---|
| Монолит с функциональными переключателями или микросервисы (+minikube/k3s) | модульный монолит + функциональные переключатели (`/admin/feature-flags`) + полноценный Kubernetes с тремя overlay: k3d(k3s) и minikube — локальный стенд, `vm` — публичный демо-стенд на k3s с TLS; доказательства живого кластера — [`k8s-evidence.md`](k8s-evidence.md) |
| Развёртывание в контуре заказчика | публичный стенд использует nip.io и Let's Encrypt только для демо; в контуре заказчика — корпоративный DNS, ingress-контроллер кластера заказчика и сертификат внутреннего CA, меняется один overlay, код и `base` — нет; компонент `prod-hardening` отключает нагрузочный клиент Keycloak ([`../design/deployment.md`](../design/deployment.md) §4.4) |
| Кэш KeyDB (легковеснее Redis): карточки, документы, страницы; без оффлайн-режима | cache-aside `crm:v1:*` (карточки, списки, панели, отчёты), TTL-коды бота, pub/sub для SSE; деградация в PostgreSQL при недоступности; каталог ролей — в памяти процесса (TTL 5 с, сброс по `access.changed`); оффлайн-режима нет |
| Нагрузка: собственный отчёт; план масштабирования на 300+ | k6-сценарий 300→400 VU с порогами SLA (`deploy/load/`), HPA backend 2→6, расчёт ёмкости ([`../design/deployment.md`](../design/deployment.md) §8); отчёт прогона — [`load-report.md`](load-report.md); замер массового переноса заявок 1 000 / 10 000 / 50 000 — [`migration-benchmark.md`](migration-benchmark.md) |
| Надёжность при повторах и обрывах связи | сквозной `Idempotency-Key` для мутаций API: повтор того же действия возвращает сохранённый ответ (`Idempotent-Replayed: true`), а не дубль операции; клиент выдаёт ключ по отпечатку действия и сам повторяет при сетевых ошибках, 502/503/504 и `409 workflow_busy` ([`../design/api-contract.md`](../design/api-contract.md) §1.6) |
| Диаграммы: C4/BPMN, связей, программно-аппаратная, БД | C4 контекст+контейнеры, ERD ×4, sequence/state, топология и DMZ-контур — по всем документам `../design/` |
| Мобильная версия не нужна — адаптивная вёрстка | адаптив до планшета, перетаскивание карточек с сенсорного экрана; новые экраны («Активность КАМов», «Роли и права») свёрстаны под ширину 375 px без горизонтальной прокрутки: дерево отчёта на телефоне — аккордеон карточек, редактор роли — одна колонка; мобильного приложения нет |
| LLM — только если реально дополняет; не приоритет | не делаем; переключатель `llm_features` выключен с подписью «в закрытом контуре — выключено»; выводы в сводке отчёта КАМов строятся детерминированными правилами |
| Ранжирование программ — ручное; автоформула — бонус | `priority_rank` (меньше = выше), перетаскивание/▲▼ с аудитом; расчётный режим — за функциональным переключателем |
| Встроенный обмен сообщениями: в идеале да, заглушки допустимы | комментарии заявки: @упоминания, вложения из MinIO, обновление в реальном времени по SSE |
| Удобство интерфейса важнее брендбука | токен-слой Tailwind v4 + shadcn/ui под дизайн-систему «Ростелекома» gen2 ([`../design/redesign.md`](../design/redesign.md), [`../design/brand-rt.md`](../design/brand-rt.md)), туры адаптации сотрудников, принцип «ноль тупиков» |

## Telegram-бот

| Требование | Где реализовано |
|---|---|
| Служба уведомлений с абстракцией каналов: Telegram (реальный), Max/Email — подключаемые | `services/notification`: адаптеры каналов; статусы active/stub в настройках |
| Авторизация бота через тот же Keycloak, привязка по одноразовому коду | код 6 цифр (TTL 10 мин, KeyDB GETDEL) → бот под client credentials `crm-notification` → `POST /internal/bot/bind` → `app_user.tg_chat_id` |
| Команды бота — строго по ролевой модели | `/my`, `/stuck`: backend резолвит chat_id → пользователь и применяет его права и область (процессы, «только свои»); непривязанный получает отказ |
| «Зависшие»: настраиваемый порог 1–2 недели, эскалация ответственному и руководителю | порог в днях (по умолчанию 14, каскад правило→этап→процесс→настройка); 1×порога — ответственному, 1.5× — руководителю (`manager_id`); дедупликация уведомлений |
| Адресация: по нику Telegram, email или роли — настраиваемо | `notification_rule.recipient_type`: responsible / manager / role / user / tg_username / email; по роли — любая роль каталога, уведомление получают только те, кто видит процесс заявки |
| Закрытый контур: шлюз уведомлений в DMZ, отразить на диаграмме | NetworkPolicy: notification — единственный egress; диаграмма в README и [`../design/deployment.md`](../design/deployment.md) §3.11 |

## Осознанно за рамками системы

Оффлайн-режим, мобильное приложение, ЭЦП, обогащение из интернета во время
работы, версионирование процессов — отсутствуют в схеме БД, API и интерфейсе
**намеренно**, в соответствии с техническим заданием.
